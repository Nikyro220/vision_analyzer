========================================================
POST /analyze — analyze image(s) for risk signals
========================================================
Request body is one of two forms:

  (a) a raw image in the request body, Content-Type: image/*
  (b) multipart/form-data with fields:
        images     — one or more images (required)
        backend    — 'vllm' | 'ollama' (optional, overrides BACKEND)
        model      — model name/id (optional, otherwise auto-detected)
        lang       — 'ru' | 'en' (optional, language for this request
                     only — does not change the global default)
        categories — optional one-off categories for this call, see
                     POST /analyze — one-off categories below

backend/model/lang can also be passed as query parameters — works
for both form (a) and (b):
  ?backend=vllm&model=google/gemma-4-31B-it&lang=en

Examples:

  # 1) Simple analysis, image straight in the body, everything default
  curl -X POST -H "Content-Type: image/" \
    --data-binary "@/path/to/file.png" \
    http://xxx.xxx.xxx.xxx:6769/analyze

  # 2) Same, but the model answers in English (this request only)
  curl -X POST -H "Content-Type: image/" \
    --data-binary "@/path/to/file.png" \
    "http://xxx.xxx.xxx.xxx:6769/analyze?lang=en"

  # 3) Explicit backend and model via query parameters
  curl -X POST -H "Content-Type: image/" \
    --data-binary "@/path/to/file.png" \
    "http://xxx.xxx.xxx.xxx:6769/analyze?backend=ollama&model=llama3.2-vision"

  # 4) Several images at once, via multipart
  curl -X POST \
    -F "images=@/path/to/file1.png" \
    -F "images=@/path/to/file2.jpg" \
    http://xxx.xxx.xxx.xxx:6769/analyze

  # 5) Multipart, with backend/model/lang passed as separate form fields
  curl -X POST \
    -F "images=@/path/to/file.png" \
    -F "backend=vllm" \
    -F "model=google/gemma-4-31B-it" \
    -F "lang=en" \
    http://xxx.xxx.xxx.xxx:6769/analyze

========================================================
GET/POST /config — view/change backend, ollama_host, vllm_url
========================================================
GET returns the current values. POST accepts 'backend',
'ollama_host' and/or 'vllm_url' (any subset, at least one) — via
query, JSON body or form field, same as /lang. Takes effect
immediately, no server restart needed. Startup values can also be
set via the VISION_ANALYZER_BACKEND / _OLLAMA_HOST / _VLLM_URL
environment variables.

  curl http://xxx.xxx.xxx.xxx:6769/config

  curl -X POST "http://xxx.xxx.xxx.xxx:6769/config?vllm_url=http://192.168.1.10:8000/v1"

  curl -X POST -H "Content-Type: application/json" \
    -d '{"backend": "ollama", "ollama_host": "http://192.168.1.10:11434"}' \
    http://xxx.xxx.xxx.xxx:6769/config


========================================================
GET/POST /sampling — view/change temperature, top_p, top_k, seed, num_ctx, num_predict, think
========================================================
GET returns the current values. POST accepts any subset of
'temperature', 'top_p', 'top_k', 'seed', 'num_ctx', 'num_predict',
'think' — via query, JSON body or form field, same as /config. Takes effect immediately, for
every subsequent /analyze request. Startup values can also be set via
the VISION_ANALYZER_TEMPERATURE / _TOP_P / _TOP_K / _SEED / _NUM_CTX / _NUM_PREDICT / _THINK
environment variables.

num_ctx is the context window size, relevant only for backend=ollama
(vLLM's context size is fixed at server startup and is not a
per-request parameter). By default it is NOT overridden (null) —
Ollama uses the model's own default from its Modelfile, same as
before /sampling existed. IMPORTANT: raise it deliberately — a large
num_ctx noticeably increases KV-cache size and prefill time, and can
cause request timeouts if VRAM runs short. Mainly useful for a long
/analyze -> history.

  curl http://xxx.xxx.xxx.xxx:6769/sampling

  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?temperature=0.2&top_p=0.9"

  # raise context for a long history
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?num_ctx=8192"

  # revert to the model's default (auto/none/default/empty all work)
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?num_ctx=auto"

num_predict is the maximum number of tokens the model may generate in
one answer (Ollama: options.num_predict; vLLM: max_tokens). Must be at
least 1. By default it is NOT overridden (null) — the model's own limit
applies. Too small a value cuts the JSON report off mid-way (you get
"_raw" instead of a report) — 1024-2048 is a sensible minimum. With
think enabled, reasoning tokens count towards this limit too.

think controls the model's reasoning mode. Most models take true/false;
GPT-OSS takes only the levels low / medium / high (true/false is ignored
for it, and its reasoning cannot be fully disabled). Default: false.
On vLLM the value is sent as chat_template_kwargs.enable_thinking, so a
level only means "on" there, and without --reasoning-parser the
reasoning text may end up inside the answer itself.

  # cap the answer length
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?num_predict=2048"

  # remove the limit again (auto/none/default/empty all work)
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?num_predict=auto"

  # reasoning: off / on / GPT-OSS level
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?think=false"
  curl -X POST "http://xxx.xxx.xxx.xxx:6769/sampling?think=high"

vllm_context_window (in the GET response) — read-only, the context
size actually reported by vLLM (GET /v1/models -> max_model_len), or
null if the backend is unreachable or that particular build doesn't
expose the field. When it's known, history sent to backend=vllm is
automatically truncated (a rough estimate, no real tokenizer) to fit
that size — the truncation is logged on the server (WARNING).

========================================================
GET /categories/<name> — one category's full content
========================================================
Returns summary, full, compact and (if present) examples for a single
category:

  curl http://xxx.xxx.xxx.xxx:6769/categories/weapons_and_dangerous_objects


The categories above are read-only through this API — there is no
endpoint to create, edit or reorder them permanently (they're edited
by hand in inference/categories/ on the server). To use a category
for a single /analyze call without touching the shared defaults, see
POST /analyze — one-off categories below.


========================================================
POST /analyze — conversation history (for UI/bots)
========================================================
The server itself stores NO history at all — it is sent in full by
the client on every request via the 'history' field: a JSON array of
prior messages in a backend-agnostic format:

  [
    {"role": "user", "content": "...", "images": ["data:image/png;base64,..."]},
    {"role": "assistant", "content": "..."}
  ]

'content' and 'images' are optional. 'images' are data URLs (plain
base64 with no prefix also works). 'history' can be passed via query
(as a JSON string), a multipart field (as a JSON string), or in the
new JSON body (see below) — already as a plain array.


========================================================
POST /analyze — form (c) JSON body (convenient for UI clients)
========================================================
Content-Type: application/json, fields:
  image      — a single image, base64 or data URL
  images     — a list of images (alternative to 'image')
  backend, model, lang — same as before, all optional
  history    — optional conversation history (see above)
  categories — optional one-off categories for this call (see below)

  curl -X POST -H "Content-Type: application/json" \
    -d '{"image": "data:image/png;base64,....", "lang": "en", \
         "history": [{"role": "user", "content": "previous message"}]}' \
    http://xxx.xxx.xxx.xxx:6769/analyze


========================================================
POST /analyze — one-off categories (not saved on the server)
========================================================
'categories' lets you add or override a risk category for a SINGLE
/analyze call, without touching the server's shared defaults (see
GET /categories above — those stay read-only through the API). The
server never stores what you send here: nothing is written to disk,
and no other request — from you or anyone else — ever sees it. Each
call builds its own private copy of the category list from scratch.

How each category behaves:
  - a NAME THAT ALREADY EXISTS in the defaults (weapons_and_dangerous_
    objects, extremist_or_hate_symbols, self_harm_or_violence_indicators,
    illegal_activity_indicators, minor_in_risk_context) REPLACES that
    default for this call only. You can omit any field (summary/full/
    compact/examples) — an omitted field falls back to the default's
    current value, so you can override just one part (e.g. only the
    summary) and leave the rest as-is.
  - a NEW NAME is ADDED alongside the defaults. summary, full and
    compact are all required for a new name (there is nothing to fall
    back to).
  - either way it goes through the exact same two-pass pipeline as the
    built-in categories: it's offered to the first (classifying) call
    as a candidate via its 'summary', and only if the model selects it
    does its 'full' (or 'compact', in the no-history fallback) text
    get included in the second, full-analysis call.

Fields per category (same shape as GET /categories/<name>):
  name      — required, category identifier (letters/digits/'_' only)
  summary   — short text shown to the first (classifying) pass
  full      — the full <signal_category>...</signal_category> rules
              block, used in the normal (non-fallback) second pass
  compact   — a shortened version of the same rules, used only in the
              no-history/all-categories fallback pass
  examples  — optional, {"en": "...", "ru": "..."} example scenes

Tip: since 'summary' is what actually decides whether the classifying
pass picks the category, wording it as an unconditional instruction —
e.g. "Include this category in every case, regardless of what is in
the image; THIS CATEGORY IS MANDATORY" — reliably makes the model
select it on every call, which is a simple way to force a rule to
always apply without touching the defaults.

'categories' can be sent three ways, and they can be mixed within one
call:

  1) JSON body — a plain array, each item a full category object:

     curl -X POST -H "Content-Type: application/json" \
       -d '{"image": "data:image/png;base64,....", \
            "categories": [{"name": "my_temp_category", \
              "summary": "...", \
              "full": "<signal_category name=\"my_temp_category\">...</signal_category>", \
              "compact": "..."}]}' \
       http://xxx.xxx.xxx.xxx:6769/analyze

  2) multipart — one file per category, similar to (but not the same
     as) the per-category files in inference/categories/ on the
     server: those split "name" (the filename) and "summary" (kept in
     index.json) out separately, while here all five fields
     ("name", "summary", "full", "compact", "examples"?) live together
     in one flat JSON object per file. No need to parse anything
     client-side — just attach the file as-is. Repeat the 'categories'
     field to send several at once:

     curl -X POST \
       -F "images=@/path/to/photo.jpg" \
       -F "categories=@watermark_or_overlay_text.json" \
       -F "categories=@another_rule.json" \
       http://xxx.xxx.xxx.xxx:6769/analyze

     A single multipart file may also contain a JSON array of several
     categories instead of one object — it gets expanded the same way.

  3) query parameter — a JSON string, same shape as one multipart
     file's content; repeat 'categories=' to send several:

     curl -X POST -H "Content-Type: image/*" --data-binary "@photo.jpg" \
       "http://xxx.xxx.xxx.xxx:6769/analyze?categories=%7B%22name%22%3A%22my_temp_category%22%2C...%7D"

Overriding an existing default's summary only, leaving full/compact
as they are on disk:

     curl -X POST -H "Content-Type: application/json" \
       -d '{"image": "data:image/png;base64,....", \
            "categories": [{"name": "weapons_and_dangerous_objects", \
              "summary": "Updated summary text, just for this call."}]}' \
       http://xxx.xxx.xxx.xxx:6769/analyze

A malformed 'categories' entry (missing 'name', or a brand-new name
missing summary/full/compact) fails the whole request with a 400 and
does not run any analysis.
